# 6. Implementation

The implementation continues the approved design rather than choosing a new product or platform. It is a C++17 console application with a separate HTTP server, SQLite persistence and a local submission-file store. The user confirmed that Gate 2 had been approved before implementation began. The supplied reports remain the baseline for planning, requirements and design. Their proposed refinements DA1, DA2 and DA3 are addressed explicitly: extensions after marking are refused; plain HTTP remains a disclosed isolated-LAN limitation; fractional marks are supported without rounding before the penalty calculation. The source is divided into domain, service, repository, API and client files, with CMake defining the build.

The domain layer implements an abstract User with Student, Lecturer, HeadOfDepartment and Administrator subclasses. Each subclass implements getRole and isPermitted. UserFactory constructs the appropriate object from the persisted role. Services receive a User reference and ask it for permission before checking course, department or ownership scope. This makes polymorphism meaningful: a lecturer cannot become an administrator merely by crafting another menu action or HTTP request. The Principal is a requirements stakeholder, not a fifth operational account role. This distinction corrects the informal four-actor wording in the initial feasibility discussion by following the case study and the detailed week 2 SRS.

The late-penalty Strategy is IPenaltyPolicy with TieredDailyPenaltyPolicy. The effective deadline and submission time come from server-controlled data. Positive lateness is rounded upwards into days. Exactly twenty-four hours gives one day, while twenty-four hours plus one second gives two. At three days the deduction is thirty percent of the assignment maximum; beyond three days the final mark is zero. A low raw mark cannot become negative. Marking and HoD adjustment use the same calculation. The application never accepts a client-supplied final mark or penalty, so staff discretion is expressed through an extension or a justified raw-mark adjustment rather than an invisible penalty override.

SubmissionLifecycle guards allowed events. A new submission becomes SUBMITTED or LATE; only an unmarked on-time submission may be replaced before its effective deadline. Replaced files remain in increasing sequence order. Marking requires a finite raw mark within the assignment maximum and non-empty written feedback. Moderation may approve, adjust with a reason, or return work for re-marking. Returned work remains MARKED with a flag, and cannot be approved until the lecturer has re-marked it. A moderated or released mark cannot be edited. Students receive a filtered response containing no raw mark, final mark or feedback until release, instead of receiving hidden values that a modified client could reveal.

All application SQL lives in repository.cpp. Services select fixed Query or Command identifiers and supply values; a statement wrapper binds those values and finalises the prepared statement through RAII. Database mutations run inside BEGIN IMMEDIATE, commit on success and roll back on exceptions. Mark changes and their corresponding audit rows share the transaction. The audit table has triggers preventing update and deletion. Each mutable submission has a version counter, and updates require the displayed version. A concurrent edit therefore produces a conflict and prompts the client to reload, rather than silently replacing another staff member's decision.

There are two deliberate deviations from the proposed infrastructure diagram. The narrow aggregate interfaces are consolidated into IRepository, and a single recursively locked SQLite connection serialises reads as well as writes. This preserves the data-access boundary and simplifies atomic collaboration between repositories, but sacrifices some interface segregation and the proposed read-pool concurrency. The deviations are documented in the design supplement and should be explained in the viva. They are not presented as an exact implementation of Figure 5.5. The observed workload results justify a usable coursework baseline, while the login shortfall demonstrates why architectural intentions alone cannot prove non-functional compliance.

Passwords are encoded using libsodium Argon2id with interactive operation and memory limits, including a fresh library-generated salt. Verification calls the recognised library API rather than implementing a comparison scheme. A condition-variable gate allows at most two simultaneous expensive hash operations, preserving the proposed memory protection. Failed-login counters and lock timestamps are persisted. Sessions use random 256-bit tokens held only in memory, expire after fifteen idle minutes, and are revoked by password reset or deactivation. The normal console client hides password input. First-run local bootstrap is intentionally simple and its visible password prompt is disclosed in the technician guide.

Files are stored using random server-generated names, with original name, size and SHA-256 recorded in the database. No client path is used as a server storage path. An upload contains between one byte and five mebibytes. Multipart input avoids base64 inflation. Review identified that a binary download cannot safely be placed directly into a JSON text field; downloads therefore use hexadecimal bytes, decoded by the client when saving. A failed transaction removes its newly written file, and startup sweeps managed files without database references. Historical referenced files remain. This design accepts some additional download bandwidth in exchange for explicit binary correctness.

The console client presents role-specific numbered actions and labelled prompts. It uses structured JSON to display results, which keeps the implementation dependency-light but is less approachable than a carefully designed form-based desktop interface. Every action is reachable directly from the role menu, but technical reachability does not establish usability for non-specialist staff. A first-time-user trial remains necessary. Input and HTTP failures return messages instead of terminating the application; EOF exits cleanly. The release includes a real executable for both server and client, build instructions and the pinned source dependencies needed to reconstruct the coursework baseline.

# 7. Verification and validation

The test plan follows the V-Model rather than treating testing as a single final execution. Unit tests verify the penalty rule, role hierarchy, UTC validation and lifecycle against the detailed design. Integration tests verify collaboration among services, SQLite persistence, file storage abstractions and audit transactions. System tests launch a real HTTP server and exercise the use-case workflow and exception paths. Automated acceptance scenarios demonstrate stakeholder-visible outcomes such as withheld marks and written feedback. They support, but cannot replace, supervisor Gate 3 review and acceptance by actual school representatives.

Equivalence partitioning separates on-time and late submissions, enrolled and unregistered students, valid and invalid marks, each user role and each lifecycle status. Boundary analysis tests one second before, exactly at and one second after a deadline, then the twenty-four-, forty-eight- and seventy-two-hour boundaries. A maximum of twenty-five demonstrates fractional penalties. Invalid numeric inputs include negative values, values above the maximum and non-finite values. File cases include empty data, the exact five-mebibyte limit and one byte beyond it. Extension tests cover equal, earlier and later deadlines, and an attempt after marking. Fixed clocks make time tests repeatable without waiting for real deadlines.

The v1.0 Catch2 suite completed fourteen named cases and 219 assertions. It covers submission history, late acceptance, denied replacement, extension reclassification, moderation return, raw-mark adjustment, stale versions, ownership and department restrictions, rollback, Argon2id, lockout, sessions and administrator operations. Twenty SQL-injection strings are passed as credential values; none authenticates or changes the account or course counts. These checks demonstrate parameter separation for the selected attack cases. They do not claim exhaustive security testing. The real HTTP suite completed seventy-seven checks, including a byte-for-byte binary download, result visibility, one audit entry per mark mutation, thirty invalid-input cases, restart recovery and backup/restore.

The system harness uses temporary synthetic instances, bootstraps an administrator and creates the remaining roles through the API. It submits a binary file, marks it, attempts out-of-department moderation, adjusts and releases the result, and then inspects the audit. The harness kills and restarts the process to demonstrate committed persistence and the loss of in-memory sessions. A separate writer is killed with an uncommitted SQLite transaction, after which the original mark and integrity check survive. That fault case verifies SQLite rollback through the repository's storage assumptions; it is not represented as a simulation of every possible server or hardware failure during every service operation.

Business-logic line coverage is measured using GCC coverage instrumentation and gcov JSON. The scope is domain.cpp and services.cpp, excluding third-party headers, the test framework, API plumbing and repository implementation. v1.0 reached 95.77 percent, above the seventy-percent target. The v1.1 suite adds the CR1 tests and its own measured coverage report. Line coverage is reported with its denominator and source scope, because execution of a line is weaker evidence than exploring all logical combinations. Boundary and authorization tests therefore remain necessary even when the numerical coverage figure is high. No whole-application coverage claim is inferred from the business-layer figure.

A separate workload stored eight hundred students and fifty staff, each with a separately salted password hash. Fifty concurrent clients authenticated and listed assignments. Eight hundred submission requests completed in 44.342 seconds, with all eight hundred stored file checksums verified and SQLite integrity returning ok. Listing latency at the ninety-fifth percentile was 0.0091 seconds. Login latency was 2.5528 seconds, exceeding the two-second requirement. The failure remains open. The workload used loopback on this workstation, without enforcing the specified two-core and four-gigabyte machine profile, and does not certify school hardware, memory limits or physical disconnection of the external network.

This performance result is informative because the security design deliberately limits hashing concurrency. Reducing memory settings simply to turn the test green would change an approved security decision and require a documented trade-off. The next experiment should profile hash latency and worker-queue delay on the target server, then compare a reviewed concurrency or scheduling change under the three-hundred-megabyte memory limit. Until that experiment is run, the correct conclusion is partial non-functional compliance, not an unsupported promise of responsiveness for all users. The report distinguishes an implemented feature, an executed test, a failed threshold and an unmeasured environment.

The defect log records the scalar JSON binding bug, unsafe binary text transport, uninitialised members, misleading indentation and over-broad login serialization. Each record identifies cause, correction and relevant retest. The scalar bug was found by integration setup before successful workflow runs. Binary handling was corrected before the system round-trip check. Static-analysis warnings were fixed and the analyser rerun. Retaining this sequence provides evidence that verification influenced implementation. It avoids the misleading impression that the first version was perfect. Gate 3 remains a real supervisor review to be performed with the evidence package, including the unresolved login and usability findings.

# 9. Deployment

The deployment diagram places console clients on school PCs and a single server, database and file store on the server PC. Clients communicate only with the API and never open the SQLite file. The initial bind address is loopback, supporting a safe one-computer demonstration. A technician may choose a school LAN address and allow the port only on that network. The guide includes prerequisites, first-admin bootstrap, role and course setup, client configuration, a synthetic smoke workflow and troubleshooting. A Windows x64 package contains both executables, schema, supporting DLLs, notices and manuals. The source package retains the CMake build route for other supported environments.

Database and submission files must be backed up together. The backup command uses SQLite's backup API and copies all referenced files, including replaced versions. To maintain a consistent file/database pair, the guide requires stopping the server first. Restore uses a new database path and a new file folder, then checks integrity and downloads a sample submission. A startup orphan sweep means unrelated database and file folders must never be mixed. The stopped-service procedure is a limitation compared with a fully coordinated live backup, but is concrete and testable for a small school installation. The system harness verifies restoration rather than assuming a copied file is recoverable.

User manuals cover the administrator, lecturer, HoD and student independently. They explain exact role codes, IDs, UTC input, raw versus final marks, version conflicts, return and release, extension limits and result visibility. The student guide explains why a late first submission is accepted but a late replacement is rejected. The lecturer guide distinguishes marking from release, while the HoD guide describes skipped rows in batch release. These details support consistent operation and fair expectations. The three-user usability exercise, screen-reader compatibility and target-machine resource checks still require observation. A prepared runtime package is therefore distinguished from an operationally accepted school deployment.

# 10. Maintenance: class extensions

CR1 requests class-wide extensions and visible extension information on the student's assignment list. It is primarily perfective maintenance: it enhances the existing individual-extension workflow for a new administrative need rather than correcting an implementation defect. The impact analysis maps FR11, FR14, BR1, BR10, UC08, UC12 and UC20 to the affected domain, services, database, API, console action and tests. New requirements FR11a and FR14a specify lecturer class extension and explicit student display. The original diagrams are retained, with a supplement showing the ClassExtension association and changed resolution step rather than silently redrawing the baseline without a version history.

ClassExtension is stored once per assignment with a new deadline, reason, granting user and timestamp. The original assignment deadline is unchanged. Effective deadline is the latest of the base deadline, class extension and individual extension. This rule preserves a longer individual accommodation when a shorter class extension is granted, and allows a later class extension to benefit everyone, including students enrolled afterwards. It also avoids copying hundreds of equivalent individual-extension records, which would make later changes and provenance harder to explain. A class deadline must move forward relative to its previous value and must have a non-empty reason.

The class operation runs in one transaction. It verifies lecturer assignment, inspects all existing submissions, refuses the whole operation if any is already marked, writes the class extension and re-evaluates each unmarked submission's status. Refusing after marking preserves DA1 and the immutability of assessment snapshots; allowing the operation for only some students would be a different school policy. The decision is disclosed as a policy for school review, particularly if future emergency extensions must apply after marking. The late-penalty calculation itself does not change. No new route can write a final mark or bypass HoD approval.

Migration creates the new table idempotently for an existing v1.0 database. A specific upgrade check used the actual v1.0 executable to create an instance, then opened that instance with v1.1. It verified that the account record was unchanged, the table existed, integrity was ok and a second migration run succeeded. Two additional Catch2 cases verify individual/class precedence, visible reasons, exact-deadline reclassification, replacement, invalid deadlines, role and course restrictions and atomic refusal after marking. The original fourteen cases are rerun. The HTTP regression also creates a class extension and checks the student's effective deadline and explanation through the real API.

# 11. Professional, legal and ethical issues

Learner identities, assessment files, marks and feedback require careful handling. Lesotho's Data Protection Act is published as Act 5 of 2012, with the source text's short title referring to the Data Protection Act, 2011. The school should confirm applicable legal obligations and commencement details with its responsible officer before operational use. The design addresses practical safeguards through limited role scope, deactivated accounts rather than deleted assessment identities, audit trails and restricted backups. These controls are relevant evidence of responsible processing, but do not establish legal compliance on their own. The institution still needs lawful processing procedures, retention rules and a way to handle access or correction requests.

The assessment setting makes integrity as significant as confidentiality. A mark must not change without an identifiable actor and a reason, and a student must not see an unmoderated value that may later be withdrawn. The server therefore owns all permission and penalty decisions. However, an operating-system administrator with direct database access is outside the application's audit boundary; append-only triggers are not a substitute for server access controls and secure backup handling. Plain HTTP also leaves credentials and marks observable to someone able to inspect LAN traffic. Isolation reduces exposure but does not remove it, so TLS remains a priority before use on a shared or untrusted network.

Fairness depends on making policy visible. The ceiling rule causes a one-second delay to count as one day late, and more than seventy-two hours produces zero even if the work is educationally valuable. The application consistently applies that stated rule and still accepts the work for feedback. Consistency alone does not prove fairness. Staff must communicate deadlines, use an accessible clock/time convention and offer an accountable extension process for illness, disability or disruption. CR1 helps respond consistently to school-wide disruption while preserving longer individual arrangements. Decisions after marking require an explicit policy change rather than an undocumented workaround or manual database edit.

Accessibility also needs evidence. A keyboard console removes dependence on a mouse and avoids some visual layout barriers, but structured JSON, technical IDs and UTC input can still confuse first-time users or screen-reader users. The manual, direct menu access and clear error messages are initial measures. Actual trials should examine reading order, language clarity, error recovery, contrast settings and whether users can finish the core tasks independently. Finally, professional integrity requires the student to understand and explain this continuation, distinguish generated assistance from their own reviewed decisions as required by institutional policy, and report failed and unrun checks honestly during submission and viva.
